## What is BitaKit?

**BitaKit is a composition layer for building apps with AI agents.** Every feature is a
self-contained plugin in its own folder: its pages, behavior, settings and extension points live
together, and features meet only through explicit contracts. A developer or a coding agent adds
or extends a feature with a small, local change instead of rewiring the app.

BitaKit is not another framework. It sits on top of the one you already use, through an adapter
(Next.js today, TanStack Start experimental), which keeps routing, rendering and deployment.

<Figure name="layers" />

Work through predictable **file conventions**, or compose the same definitions directly with
the **TypeScript API**. Both use the same plugin model and runtime.

## The problem it solves

As an app grows, each new feature tends to edit shared files: a route list, a menu, a provider
tree, an event bus, a settings screen. Every edit is small, but it changes code that someone else
owns, and that is where people and coding agents collide. BitaKit gives those shared mechanisms
one owner and every feature one folder, so a new feature is mostly new files.

## Humans and AI agents, one structure

- **The path is the ID.** `src/plugins/notes/actions/archive.ts` is the Action `notes.archive`;
  `ui/pages/index.tsx` in the same folder is the page `/notes`.
- **Names are checked.** Generated types reject an unknown Action ID, service, event, setting
  key or slot name in `npm run typecheck`.
- **The same commands.** `npx bitakit add` creates files in the right place, `npx bitakit info`
  lists every ID, and `npx bitakit doctor` reports wiring problems with the fix.
- **Written-down rules.** Apps created with `@bitakit/create-app` or wired with `npx bitakit init`
  carry a one-screen `AGENTS.md` that says where each task goes. Every plugin folder from
  `npx bitakit add plugin` and every `@bitakit/*` package keeps its own `AGENTS.md` with its
  contracts and checks; the `CLAUDE.md` beside each one only imports it.

## What BitaKit is not

| BitaKit is not…         | Instead…                                                                                                                                                                   |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A framework or a router | Your framework keeps routes, rendering and deployment; one catch-all route renders plugin pages.                                                                           |
| A component library     | Core has no UI. `@bitakit/ui/components` is an optional set of standard components.                                                                                        |
| A sandbox               | Plugins are trusted code in the same app. A failing plugin is reported at startup and a failing slot component is contained, but plugins are not isolated from each other. |
| A backend               | Plugins run in your client app. Server-side plugins are planned, not shipped.                                                                                              |

## Why BitaKit?

Around every feature, an app needs navigation entries, button states, confirmations, messages,
saved settings, events and places where other features add UI. Without a shared structure,
that repetitive code is written, read back, debugged and tested again for each feature, which
costs a coding agent many tokens and makes parallel work collide in shared files. BitaKit
provides those mechanisms once, tested, so an extension like an export button is one file of
about 200 tokens.

[Read more: what it saves, with measured numbers →](/docs/why-bitakit)

BitaKit is useful when several features need these shared conventions. A small page can stay
small: you do not need every capability, an optional UI package or a full manifest to start.

## Files first, APIs when you need them

If you know file-based conventions from frameworks such as Next.js, the idea will feel familiar:
**the file's location tells BitaKit what it contributes**. In an app configured with the BitaKit
framework adapter and provider, add a supported file with its default export; discovery generates
the imports and types. You do not maintain a registration list for each new file.

```text
src/plugins/notes/
├── actions/open.ts      → Action: notes.open
├── settings.ts          → Notes preferences
└── ui/pages/index.tsx   → Page: /notes
```

These are optional additions, not a required scaffold. The same conventions give developers and
AI coding agents a shared map: Actions go in `actions/`, services in `services/`, and owned slot
definitions in `slots/`.

| How you prefer to work | How the same Action joins the Notes plugin                                                                                                     |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| File conventions       | Put a `defineAction` default export in `src/plugins/notes/actions/open.ts`.                                                                    |
| Programmatic API       | Pass that Action definition as `open` in `definePlugin({ id: 'notes', actions: { open } })`, then include the plugin in your host composition. |

Discovery runs during development and builds. It registers definitions; a page, Action binding
or mounted slot still determines where UI appears.

## How the pieces fit

1. **Keep each feature together.** Discovery connects its files and generates imports and types.
2. **Extend through declared places.** Plugins contribute Actions or UI to slots the owner exposes.
3. **Share the runtime, keep your framework.** Core owns execution, state and cleanup; React bindings
   and optional visual plugins connect that behavior to your application.

[Read more: architecture and package boundaries →](/docs/concepts/architecture)

### Clear ownership, explicit contracts

Each developer or AI coding agent can work inside the feature it owns. Plugins connect through
**service contracts, declared events and named slots**, so another feature can use or extend
them without editing their internal files.

<Figure name="feature-contracts" />

For example, Activity can listen to a Notes event and Tips can add a widget to the Notes footer.
Neither needs to rewrite the Notes page or Core. Keeping changes local reduces accidental
coupling and the risk of breaking shared foundations; compatible contracts and tests still matter.
