## What is BitaKit?

BitaKit is a TypeScript foundation for applications built from **plugins**. A plugin is one
feature: its pages, behavior, settings and extension points live together. BitaKit connects
those pieces; your framework keeps its routes and rendering.

Work through predictable **file conventions**, or compose the same definitions directly with
the **TypeScript API**. Both use the same plugin model and runtime.

Start with a plugin for your feature, then give it a page. Add an Action when it needs a button, a setting when it needs a preference,
and a slot when another plugin should be able to extend it.

## Why BitaKit?

| When your app needs… | BitaKit gives you… |
| --- | --- |
| Features that can grow independently | A plugin folder containing the feature's own files. |
| Clear locations for developers and AI coding agents | Conventional paths and generated types that make each feature easier to find and extend. |
| Several people or agents extending the app | Feature ownership and explicit contracts between plugins. |
| The same operation in several places | One Action, bound to buttons, links or menus. |
| New UI inside an existing feature | Named slots that other plugins can target. |
| Preferences with a Settings page | One declaration for saved values, fields and navigation. |
| Communication and shared observation | Events and interceptors with runtime-owned cleanup. |

BitaKit is useful when several features need these shared conventions. A small page can stay
small: you do not need every capability, an optional UI package or a full manifest to start.

## Files first, APIs when you need them

If you know file-based conventions from frameworks such as Next.js, the idea will feel familiar:
**the file's location tells BitaKit what it contributes**. In an app configured with the BitaKit
framework adapter and provider, add a supported file with its default export; discovery generates
the imports and types. You do not maintain a registration list for each new file.

```text
src/plugins/notes/
├── actions/open.ts      → Action: notes.open
├── settings.ts          → Notes preferences
└── ui/pages/index.tsx   → Page: /notes
```

These are optional additions, not a required scaffold. The same conventions give developers and
AI coding agents a shared map: Actions go in `actions/`, services in `services/`, and owned slot
definitions in `slots/`.

| How you prefer to work | How the same Action joins the Notes plugin |
| --- | --- |
| File conventions | Put a `defineAction` default export in `src/plugins/notes/actions/open.ts`. |
| Programmatic API | Pass that Action definition as `open` in `definePlugin({ id: 'notes', actions: { open } })`, then include the plugin in your host composition. |

Discovery runs during development and builds. It registers definitions; a page, Action binding
or mounted slot still determines where UI appears.

## How the pieces fit

1. **Keep each feature together.** Discovery connects its files and generates imports and types.
2. **Extend through declared places.** Plugins contribute Actions or UI to slots the owner exposes.
3. **Share the runtime, keep your framework.** Core owns execution, state and cleanup; React bindings
   and optional visual plugins connect that behavior to your application.

### Clear ownership, explicit contracts

Each developer or AI coding agent can work inside the feature it owns. Plugins connect through
**service contracts, declared events and named slots**, so another feature can use or extend
them without editing their internal files.

<Diagram name="feature-contracts" />

For example, Activity can listen to a Notes event and Tips can add a widget to the Notes footer.
Neither needs to rewrite the Notes page or Core. Keeping changes local reduces accidental
coupling and the risk of breaking shared foundations; compatible contracts and tests still matter.
