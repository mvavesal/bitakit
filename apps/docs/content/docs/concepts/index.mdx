Start with three ideas:

- A **plugin** groups a feature's files.
- A **service** provides reusable functions and data.
- An **action** exposes an operation that calls those functions.

In a configured app, add the files and write your feature's behavior. Foundation discovers the definitions and manages their lifecycle. Follow [your first plugin](/docs/concepts/plugins) to see this in two files.

## Available APIs

These guides describe the current repository APIs. Core 0.1.0 is the published baseline recorded in this repository; newer APIs, including events and action setup, require the workspace version. The application generator and other packages remain release previews.

| Concept                     | Owner                                  | Purpose                                                       |
| --------------------------- | -------------------------------------- | ------------------------------------------------------------- |
| Plugin                      | `@bitakit/core`                        | Groups contributions and declares dependencies                |
| Service                     | `@bitakit/core`                        | Shares behavior, state or resources within a runtime          |
| Action                      | `@bitakit/core`                        | Names an operation and centralizes execution and availability |
| Events                      | `@bitakit/core`                        | Notifies interested consumers within one runtime              |
| React bindings              | `@bitakit/ui`                          | Observes the runtime and binds existing controls              |
| Routing and build discovery | `@bitakit/next` or `@bitakit/tanstack` | Connects the host framework                                   |
| Preferences                 | `@bitakit/app-preferences`             | Owns confirmed settings and persistence                       |

A plugin is a runtime definition, not necessarily an npm package. One package can supply several plugins or just shared contracts. See the [package and plugin guides](/docs/packages).

```text
Host application
  → Foundation runtime
    → Plugin
      → Service: reusable operations and data
      → Action: invokes those operations
        ← React binding or headless caller
```

Start with [plugins](/docs/concepts/plugins), then [services](/docs/concepts/services) and [actions](/docs/concepts/actions). Use [events](/docs/concepts/events) when one feature needs to react to changes owned elsewhere. [Discovery](/docs/concepts/discovery) removes manual contribution imports in configured hosts.

## Choose the right concept

| If you need to…                                          | Read                                          |
| -------------------------------------------------------- | --------------------------------------------- |
| Group a feature and own its cleanup                      | [Plugins](/docs/concepts/plugins)             |
| Share data access or reusable operations                 | [Services](/docs/concepts/services)           |
| Expose an operation to callers and UI                    | [Actions](/docs/concepts/actions)             |
| React after another feature changes                      | [Events](/docs/concepts/events)               |
| Supply stable defaults and host options                  | [Configuration](/docs/concepts/configuration) |
| Register flat or nested contribution files automatically | [Discovery](/docs/concepts/discovery)         |
| Customize selected defaults or behavior                  | [Overrides](/docs/concepts/overrides)         |
| Understand inferred inputs, results and payloads         | [Type safety](/docs/concepts/type-safety)     |
| Observe execution across a feature                       | [Interceptors](/docs/concepts/interceptors)   |

For standalone Node usage without automatic discovery, the [advanced To-do walkthrough](/docs/concepts/tutorial) shows explicit composition. AppShell and authentication guides are later steps; no UI integration is needed to understand or run Core.
