**Owner:** the Node-only `@bitakit/core/discovery` entry. Framework adapters connect it to the build. Installing Core alone does not scan folders.

## Start with the feature

```text
src/plugins/todos/
  services/todos.ts
  actions/add.ts
  actions/list.ts
  configs.ts
```

Every immediate folder under `src/plugins` defines a local plugin. Its folder name is the default plugin ID. Optional `plugin.config.ts` overrides metadata and dependencies. Root app contributions live directly under `src`; they do not require a wrapper plugin.

For this example, the folder already supplies `todos`, so no manifest or explicit `id` is needed. An explicit `id` is an optional override when the inferred name does not fit your application.

## Flat or nested: the same logical feature

**Folders and dots express the same logical path.** Each row below shows two ways to name one contribution, relative to `src/plugins/todos/`.

| Nested folders            | Equivalent | Flat filename             | Same result                   |
| ------------------------- | :--------: | ------------------------- | ----------------------------- |
| `actions/add.ts`          |     =      | `actions.add.ts`          | Action `todos.add`            |
| `actions/list.ts`         |     =      | `actions.list.ts`         | Action `todos.list`           |
| `services/todos.ts`       |     =      | `services.todos.ts`       | Public service `todos`        |
| `configs/actions/list.ts` |     =      | `configs.actions.list.ts` | Config subtree `actions.list` |

The file contents stay the same. For example, a default-exported `defineAction` in either `actions/add.ts` or `actions.add.ts` registers the same `todos.add` action when no explicit ID overrides it.

### You can mix folders and dots

For the configuration of the list action, all three paths are equivalent:

```text
configs/actions/list.ts     ← nested folders
           =
configs/actions.list.ts     ← folders and dots
           =
configs.actions.list.ts     ← flat filename
```

Each resolves to `actions.list` inside the same plugin configuration. Choose one spelling per contribution; different contributions may use different styles.

<Callout title="Equivalent paths are alternatives">
  Keep only one version of each contribution. Creating both `actions/add.ts` and `actions.add.ts`
  defines the same action twice and produces a duplicate-contribution error.
</Callout>

The segments still matter: `configs.list.ts` resolves to `list`, while `configs.actions.list.ts` resolves to `actions.list`. Removing `actions` changes the configuration path; replacing a slash with a dot does not.

## Automatic loading, step by step

1. The configured build adapter discovers supported files and opted-in direct dependencies.
2. Core generates static imports, composition and TypeScript declarations.
3. The host provider consumes that generated configuration.
4. Core mounts the selected plugins, constructs services and registers actions.
5. Renderers bind to the existing action snapshots and groups.

Development integration watches file additions, changes and removals. Production changes require a new build and deployment. Browser code never scans the filesystem. Automatic registration does not automatically render a new menu group or create a route.

## IDs and filenames

| File                      | Meaning                                      |
| ------------------------- | -------------------------------------------- |
| `actions/add.ts`          | Action named `add` inside the owning module  |
| `actions.add.ts`          | Equivalent spelling of the same contribution |
| `services/todos.ts`       | Service with inferred public name `todos`    |
| `configs/actions/list.ts` | Config subtree `actions.list`                |
| `interceptors/logging.ts` | Interceptor contribution                     |

The local plugin's `actions/add.ts` becomes `todos.add`. Explicit IDs take precedence. Services retain internal module namespaces while exposing their relative path or explicit public name. Manual imports without discovery still need explicit IDs.

Root app action IDs remain unprefixed when there is no app manifest. An explicit root `src/plugin.config.ts` ID supplies a namespace. Moving a contribution can therefore change inferred identities; use explicit IDs when identity must survive a move.

## What is discovered

TypeScript and TSX contributions need a default export. Helper files without one, declaration files, `server` path segments and segments starting with `-` are excluded. Dot and directory segments are equivalent. Legacy suffixes such as `.action.ts` and `.service.ts` remain supported. Duplicate logical contributions are errors, even if their filenames use different spellings.

Discovery emits static imports and Action, Service and Config maps. It does not execute client contribution modules. Build configuration, manifests and opt-in discovery adapters are trusted build code. Excluding a server path does not make transitive server imports safe for client code.

## Collections and package discovery

Actions and services can be exported as named collections instead of separate files. Define helpers preserve callback typing. A plain action function is treated as an Action factory, not automatically as an execute callback.

Direct dependencies can opt into package discovery through exported `package.json` and Foundation metadata. Transitive dependencies do not activate automatically. A package's plugin factory describes contributions; Core acquires and disposes resources at runtime.

Generated `.foundation/` files and `foundation-env.d.ts` should stay out of Git. Native application routes remain owned by the framework. An action ID or group never creates a route or renders a menu by itself.

Use [manual composition](/docs/concepts/manual-composition) when you do not have a discovery-enabled host.

Read [overrides](/docs/concepts/overrides) before replacing a contribution, and [type safety](/docs/concepts/type-safety) for generated contracts and strict IDs.
