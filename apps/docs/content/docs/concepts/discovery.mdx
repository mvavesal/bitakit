**Owner:** the Node-only `@bitakit/discovery` package. Framework adapters connect it to the build. Installing Core alone does not scan folders.

## One feature, one folder

```text
src/plugins/todos/
├── services/items.ts         defineService   → services.todos.items
├── actions/add.ts            defineAction    → todos.add
├── events.ts                 defineEvents    → todos.changed
├── configs/limits.ts         defineConfig    → app.config.todos.limits
├── interceptors/audit.ts     defineInterceptor
├── setup.ts                  plugin setup (optional)
├── plugin.config.ts          dependencies and metadata (optional)
├── locales/en.json           { "todos": { ... } }
└── ui/
    ├── pages/index.tsx       /todos          (file path = URL)
    ├── slots/app-bar.end.tsx component placed in slot "app-bar.end"
    └── providers/query.tsx   React provider wrapped around the app
```

Every immediate folder under `src/plugins` is a plugin; its folder name is the plugin ID. Folders are the one convention: the kind comes from the folder, the name from the file path, and nested folders add segments (`actions/tasks/clear.ts` → `todos.tasks.clear`). Root app contributions live in the same folders directly under `src`; their IDs carry no prefix.

<Callout title="Legacy spellings">
  `actions.add.ts` and `add.action.ts` from 0.1, and the old `pages/`, `views/` and `providers/`
  folders, are still read with a warning. `npx bitakit migrate` rewrites them to the folder
  convention; `--dry-run` lists the changes first.
</Callout>

## What is discovered

A TypeScript or TSX file participates when it has a default export; discovery detects the export with the TypeScript parser and never executes the module. Files without a default export are reported as skipped; prefix helper files with `-` to silence that. Declaration files and anything under `server/` are excluded. Everything under `ui/` that is not in `pages/`, `slots/` or `providers/` is an ordinary component, never a contribution; everything under `ui/` is React, and nothing outside it may import React.

| File                       | Meaning                                                                  |
| -------------------------- | ------------------------------------------------------------------------ |
| `actions/add.ts`           | Action `todos.add`                                                       |
| `services/items.ts`        | Service `todos.items`, reached as `services.todos.items`                 |
| `events.ts`                | The plugin's events, `todos.<name>`                                      |
| `configs/limits.ts`        | Config subtree `limits`; `configs/actions/add.ts` configures `todos.add` |
| `interceptors/audit.ts`    | Interceptor, plugin-local by default                                     |
| `ui/pages/tasks/[id].tsx`  | Page `/todos/tasks/:id`, receives `params.id`                            |
| `ui/slots/app-bar.end.tsx` | Component in slot `app-bar.end`                                          |
| `ui/providers/query.tsx`   | React provider `todos.query`                                             |

A default export may also be a record of definitions (`actions/index.ts` exporting `{ add, clear }` equals two files). Duplicate logical paths are errors that name both files. Class and factory action exports are not discovered.

## Automatic loading, step by step

1. The framework adapter (`withBitaKit` in `next.config.ts`, `bitakit()` in `vite.config.ts`) runs discovery before the build and watches during development.
2. Discovery writes `src/bitakit.gen.tsx` (`createBitaKitConfig()`, `BitaKitProvider` and the typed `ServiceMap`, `ActionMap`, `EventMap`, `ConfigMap` and `SlotMap`), `src/bitakit.gen.css` (styles of installed packages) and `src/bitakit.gen.messages.json` (plugin locales).
3. The root layout renders `<BitaKitProvider>` from `@/bitakit.gen`, which mounts the runtime.
4. Core creates the services, registers the actions and installs interceptors and UI.
5. Bindings read the live action state and service stores.

Ignore `src/bitakit.gen.*` in Git. Production changes require a new build. Browser code never scans the filesystem. Automatic registration does not create a route or render a menu by itself; a page comes from `ui/pages`, a navigation entry from `groups: ['navigation']`.

`npx bitakit info` lists what discovery finds; `npx bitakit doctor` checks the wiring, pages, links, service names and styles; `npx bitakit generate [--watch]` runs the generator by hand.

## `plugin.config.ts` and `bitakit.config.ts`

`plugin.config.ts` is optional. It declares `dependencies`, display `metadata`, an `id` other than the folder name and `entries` that relocate a kind. Discovery derives everything else.

`bitakit.config.ts` configures discovery for the whole app:

```ts
import { defineBitaKit } from '@bitakit/discovery';

export default defineBitaKit({
  configOverrides: { todos: { limits: { maxItems: 50 } } },
  actions: { overrides: { 'todos.clear': { enabled: false } } },
  plugins: { overrides: { demo: { enabled: false } }, include: { notes: '../notes/src' } },
  packages: { '@bitakit/quick-search': false },
  slots: ['dashboard.content'],
});
```

Other options: `directory` and `plugins.directory` move the roots, `plugins.autoEnable: false` turns plugins off unless enabled, `interceptors.enabled` selects app interceptors, `strict: false` allows unknown action IDs, `groups` declares action groups and `kinds` adds integration contribution kinds. See [overrides](/docs/concepts/overrides).

## Installed packages

A package becomes a plugin by declaring `bitakit: { plugin: './plugin' }` in its `package.json`. Direct dependencies and the plugin packages they depend on are activated; the package's styles join `bitakit.gen.css`. `bitakit build` produces that entry from the same folders apps use, so a plugin can move between `src/plugins/<id>` of an app and `src/` of a package unchanged. Installing an arbitrary npm dependency does not activate it.

Use [manual composition](/docs/concepts/manual-composition) when you do not have a discovery-enabled host, and read [type safety](/docs/concepts/type-safety) for the generated contracts.
