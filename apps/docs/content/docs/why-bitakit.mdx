Every app needs the same things around its features: a frame with navigation, a search dialog,
buttons that show progress and confirm, settings that persist, themes, a sign-in layout, 404 and
error screens. Usually you, or your coding agent, write them again for each app and touch them
again for each feature.

BitaKit is a composition layer on top of Next.js that ships those parts once, tested. Every
feature is a plugin in its own folder that meets the rest only through explicit contracts. You
and your agent write the feature; the app around it is already there.

## The same Todo app, two ways

Take a Todo app with what users expect today: the list, buttons that show progress and ask before
deleting, a frame with navigation, a Mod+K search dialog, saved settings with a settings page, themes,
a sign-in layout and 404 and error screens.

<Figure name="todo-comparison" />

|                                             | Hand-written (estimate)                    | With BitaKit                               |
| ------------------------------------------- | ------------------------------------------ | ------------------------------------------ |
| Code your agent writes                      | ≈14,200 tokens                             | **2,245 tokens** (measured)                |
| Agent session, reading and retries included | ≈710,000 tokens                            | **≈210,000 tokens**                        |
| AI cost at Claude Opus 5.5 list prices      | ≈$4.00                                     | **≈$1.20**                                 |
| A developer without an agent                | 2–3 days                                   | **2–4 hours**                              |
| Shared files every new feature edits        | Menu, search dialog, settings page, routes | **None**                                   |
| Infrastructure tests to write and maintain  | Settings, themes, search, dialogs, toasts  | **None**: the packages ship with 555 tests |

That is the first app. The real difference comes after it.

## The gap grows with every feature

In a hand-written app every new feature adds its entry to the shared files: the menu, the routes,
the search index, the settings page. So each next feature has more shared code to read, edit and
test again, and its agent session costs more than the last. A BitaKit feature is its own folder:
the 50th costs about what the first did.

<Figure name="feature-growth" />

| After…      | Next feature, hand-written | Next feature, BitaKit | All sessions so far, hand-written | All sessions so far, BitaKit |
| ----------- | -------------------------: | --------------------: | --------------------------------: | ---------------------------: |
| 10 features |               ≈395K tokens |          ≈137K tokens |                ≈4.1M tokens, ≈$23 |            ≈1.6M tokens, ≈$9 |
| 20 features |               ≈520K tokens |          ≈137K tokens |                ≈8.7M tokens, ≈$49 |           ≈3.0M tokens, ≈$17 |
| 50 features |               ≈895K tokens |          ≈137K tokens |                ≈30M tokens, ≈$170 |           ≈7.1M tokens, ≈$40 |

At 50 features the next one costs about 6.5 times as much hand-written, and the project so far
about 4 times as much. The table counts tokens only. With several developers or agents, the same
shared files also become merge conflicts, longer reviews and regressions in features nobody
touched; with BitaKit each of them works in a folder of their own.

<Callout title="How we estimated">

These are rough numbers to show the size of the difference, not a benchmark.

- **BitaKit column:** measured from the sample apps' files ([Todo](/docs/examples#todo),
  [Settings](/docs/examples#settings), [Theme](/docs/examples#theme) and
  [Layouts](/docs/examples#layouts)) with the open o200k tokenizer.
- **Hand-written column:** our estimate for the same capabilities on Next.js with standard
  libraries: shadcn/ui, next-themes, sonner, cmdk and a persisted store. Both columns leave out
  the framework scaffold.
- **Agent session:** about 50 tokens processed for every token of code kept (reading files,
  context resent each turn, checks and retries). BitaKit's agent also keeps the rules it reads,
  `AGENTS.md` and the skill entry (about 3,900 tokens), in context for about 25 turns.
- **Cost:** Claude Opus 5.5 list prices, $4 per million input and $20 per million output tokens,
  with 90% input. Prompt caching lowers both columns.
- **The next feature:** an agent session costs about 25 turns times what it keeps in context.
  With BitaKit that is measured and stays flat: the rules, a complete feature (the Workspace
  `notes` plugin, about 1,400 tokens) and its `AGENTS.md`. Hand-written, we estimate the feature
  with its tests (3,000 tokens), a similar feature read as the pattern (3,000) and the shared
  menu, route, search and settings files it edits (5,300 at the start, plus 500 per feature).
  The turns are equal on both sides, although checks that name the fix usually shorten
  BitaKit sessions.

Run `npm run measure:onboarding` in the repository to reproduce every number.

</Callout>

## What goes wrong in large apps, and what BitaKit does about it

Large apps built with coding agents run into the same problems again and again. Research on long
contexts shows that models [grow less reliable as their input gets longer](https://www.trychroma.com/research/context-rot),
GitClear's analysis of changed code found that [copy-pasted code now exceeds moved, refactored code](https://www.gitclear.com/ai_assistant_code_quality_2025_research),
and the Thoughtworks Technology Radar warns that agents [accelerate drift from the intended architecture](https://www.thoughtworks.com/radar/techniques/architecture-drift-reduction-with-llms)
by copying whatever patterns they find. BitaKit answers each of these with a mechanism, not a
convention someone has to remember:

| Problem in a large app                                                                      | What BitaKit does                                                                                                                                       |
| ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The agent has to read more and more of the codebase, and gets worse at it                   | A task fits in one plugin folder, its `AGENTS.md` and the contracts it uses. The skill opens its references only for the task at hand.                  |
| Every feature brings its own toasts, confirm dialogs, stores and settings forms             | These exist once, in tested packages. An Action declares `confirm`, `success` and `enabled`; a setting is one line in `settings.ts`.                    |
| Agents copy whatever pattern they find, so the architecture drifts                          | There is one shape per kind of thing (`defineAction`, `defineSettings`, slots). `npx bitakit add` writes it in the right place; types reject wrong IDs. |
| Parallel developers and agents edit the same menu, routes and registries                    | There is no shared registry. Features meet only through services, events, slots and settings.                                                           |
| Features reach into each other's internals and shared stores                                | Services have typed contracts (`provides`, `requires`); `npx bitakit doctor` names a contract nobody provides.                                          |
| A rule over all operations (duplicates, permissions, tracing) is patched into every handler | An interceptor in its own folder gates or observes any Action or service call.                                                                          |
| One broken component takes the whole page down                                              | `<PluginSlot>` renders each entry inside its own error boundary; the rest of the page keeps working.                                                    |
| Vendor SDKs for auth, data or content spread through every feature                          | Integrations are plugins behind contracts, so features use `auth` or a data service, not the vendor's SDK.                                              |
| Features look, behave and read differently                                                  | One frame, theme tokens and layouts for all; each plugin ships its own translations, merged by discovery.                                               |
| Nobody knows any more what the app contains                                                 | `npx bitakit info --json` lists every plugin, Action, service, event, slot and setting; `npx bitakit slots` shows where UI can go.                      |

## A complete app that stays flexible

One command creates a Next.js app with the frame, a settings area, light and dark themes, a
Mod+K search dialog and, if you like, the Todo sample:

```npm
npm create @bitakit/app@latest my-app -- --framework next --sample --yes
```

None of it is a fixed template. Each part is a package with settings, slots and replaceable
screens, so you change it from your own files instead of forking it. Every plugin you add plugs
into the same frame: one navigation Action puts its page in the menu and in search, and its
`settings.ts` gets a settings page.

## Anyone can extend your app

A plugin offers places where others may add UI, called slots, and announces what happened through
events. Another plugin, written by you, a colleague, an agent or a package author, fills those
places from its own folder. The owner's code does not change.

<Figure name="plugin-extension" />

The [Workspace sample](/docs/examples#workspace) has four plugins. Three of them extend the first
without editing it:

| Plugin     | What it adds                                                                     | Files | Tokens |
| ---------- | -------------------------------------------------------------------------------- | ----: | -----: |
| `notes`    | The feature: service, event, setting, two slots, page, search source             |    10 |  1,359 |
| `activity` | A feed below the notes and a count in the header, from the `notes.changed` event |     3 |    357 |
| `export`   | An "Export as Markdown" button in the notes toolbar                              |     1 |    207 |
| `guard`    | Skips duplicate notes and traces every notes call                                |     2 |    202 |

<PluginSizes />

Delete `activity`, `export` or `guard` and the app still works without it. See
[Extend a plugin](/docs/guides/extend-a-plugin).

## Work together without conflicts

Every feature lives in `src/plugins/<name>/`, and the path is the ID: `notes/actions/add.ts` is
the Action `notes.add`. Features meet only through contracts: a service, an event, a slot or a
setting. So each developer or agent concentrates on one folder:

<Figure name="parallel-work" />

```text
src/plugins/
├── notes/      owner: the feature
├── activity/   listens to notes.changed, fills notes.footer
├── export/     adds an Action to notes.toolbar
└── guard/      intercepts notes.add
```

There is no route list, menu file or registry that everyone edits at the same time, so pull
requests rarely touch the same lines. `npm run typecheck` catches a misspelled ID across folders,
and `npx bitakit doctor` reports a slot or service that nobody provides.

## Change or replace any part

Replacing a part never means editing the code that renders it. You add a file, and BitaKit picks
it:

| To change…                      | Add or edit                                                            |
| ------------------------------- | ---------------------------------------------------------------------- |
| The sign-in or onboarding frame | `src/layouts/<family>.tsx` or a variant in `src/layouts/<family>/`     |
| The 404 or error screen         | `src/ui/slots/screen.not-found.tsx` or `screen.error.tsx`              |
| The colors                      | A theme in `src/themes/<name>.json`                                    |
| A plugin's settings page        | `ui/settings/page.tsx` in that plugin                                  |
| A part another plugin renders   | A candidate file, and `choose` in `bitakit.config.ts` when several fit |

## Made for coding agents

- **One place per task.** `AGENTS.md` maps each task to a path: a page goes to `ui/pages/`, a
  button to `actions/`, a preference to `settings.ts`.
- **Commands instead of guesses.** `npx bitakit add` creates the file in the right place,
  `npx bitakit info --json` lists every ID, `npx bitakit slots` shows where UI can go.
- **Checked results.** Generated types and `doctor` turn a wrong name into an error with the fix,
  not a blank screen.
- **Everything explains itself.** `node_modules/@bitakit/<name>/AGENTS.md` describes what each
  package offers, and every plugin keeps an `AGENTS.md` with its contracts and checks.

A generated app gives agents one screen of rules in `AGENTS.md` (about 800 tokens) and the BitaKit
skill (about 3,000 tokens, with focused references of about 25,000 tokens that it opens only for
the task at hand). See [Work with AI coding agents](/docs/guides/ai-agents).

rendering and deployment, and a plugin is plain TypeScript and React in your repository.

## When BitaKit is not the right tool

- **A small app with one or two screens.** You can still start with BitaKit, but the benefit
  grows with the number of features and contributors.
- **You need isolation between untrusted plugins.** Plugins are trusted code in the same app. A
  failing slot component is contained, but plugins are not sandboxed.
- **Server-side plugins.** Plugins run in the client app today; server plugins are planned.
- **Another UI framework.** The React bindings and adapters cover Next.js and, experimentally,
  TanStack Start.
