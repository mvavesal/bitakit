Core owns the `AuthService` contract. Optional provider plugins supply the session;
`@bitakit/ui` observes it and uses the existing framework navigation binding.
There is no second session store. Server authentication and authorization remain
with the provider; server operations receive the verified identity from the app's
[`requestContext` provider](#server-identity-the-requestcontext-provider).

## Better Auth and application paths

This assumes the Better Auth adapter and the generated BitaKit provider are already
configured. Keep the provider's existing client and server setup. The `authClient` import
below refers to the application's existing client module; adjust that path to your project.

```ts
// src/configs/better-auth.ts
import { defineConfig } from '@bitakit/core';
import type { BetterAuthOptions } from '@bitakit/better-auth';

export default defineConfig({
  defaults: {
    paths: { signIn: '/account/login', afterSignIn: '/customers', afterSignOut: '/' },
  } satisfies BetterAuthOptions,
});
```

```ts
// src/services/better-auth-client.ts
import { defineService } from '@bitakit/core';
import { betterAuthClient } from '@bitakit/better-auth';
import { authClient } from '@/lib/auth-client';

export default defineService(() => ({ client: authClient }), { provides: betterAuthClient });
```

Paths are application-owned, safe root-relative URLs. No routes are created.
`useAuth().signIn({ returnTo })` navigates to the configured login page with a
`returnTo` query parameter, unless the adapter supplies a native `signIn` handler.
External or login-loop return destinations fall back to `afterSignIn`.

The login page must pass `resolveAuthReturnTo(paths, returnToFromURL)` to the native
provider login API as its completion destination. `afterSignIn` is a fallback,
not an automatic session-change redirect. Providers requiring absolute callbacks
should resolve the validated path against the configured **application** origin,
not the authentication-server origin. Keep secrets and server configuration on the server.

```tsx
'use client';
import type { ReactNode } from 'react';
import { AuthBoundary } from '@bitakit/ui';
import { LoadingPage, ErrorPage } from '@bitakit/shell/pages';

export function ProtectedContent({ children }: { children: ReactNode }) {
  return (
    <AuthBoundary pending={<LoadingPage />} renderError={() => <ErrorPage />}>
      {children}
    </AuthBoundary>
  );
}
```

`useAuth` from `@bitakit/ui` exposes the current snapshot and `signIn`/`signOut`. Bind
these methods through your existing controls and handle rejected promises through the host's
error presentation.

`AuthBoundary` waits for pending session resolution and does not redirect on session
errors. `redirect={false}` allows host-owned unauthenticated presentation. It is a
client rendering convenience, never a security boundary. Keep native server checks.
`useAuth().signOut()` awaits the adapter and then navigates to `afterSignOut`;
the boundary does not race that operation with a login redirect. A subsequent
protected route can start login normally. Calling a native SDK or service directly
does not invoke this UI navigation policy. Configure only one owner for logout navigation.

## Writing another adapter

Implement the existing `AuthService` and register it as a service that `provides` the
`authService` contract, in an ordinary plugin. No Core change, provider registry or host
bootstrap is needed. The following is an adapter template: `source` is a normalized SDK
bridge that the adapter author implements using their provider's public APIs, not an
Auth.js or Clerk API.

```ts
import {
  authService,
  configureAuthPaths,
  definePlugin,
  defineService,
  type AuthPaths,
  type AuthService,
} from '@bitakit/core';

export function customAuthPlugin(source: AuthService, paths: AuthPaths) {
  const signIn = source.signIn?.bind(source);
  return definePlugin({
    id: 'custom-auth',
    services: {
      // Reached as services['custom-auth'].session and, through the contract, services.auth.
      session: defineService(
        (): AuthService => ({
          paths: configureAuthPaths(paths),
          getSnapshot: () => source.getSnapshot(),
          subscribe: (listener) => source.subscribe(listener),
          signOut: () => source.signOut(),
          ...(signIn ? { signIn } : {}),
        }),
        { provides: authService },
      ),
    },
  });
}
```

Inside a plugin folder the same service is `services/session.ts` with the options as the
second argument; discovery derives the ID.

The bridge must return a stable `{ user, pending, error, organizationId? }` snapshot until it changes;
`user` contains at least `id`, and `null` means signed out only once `pending` is false
and `error` is absent. Subscribe to native SDK updates and return an unsubscribe
function. Preserve SDK failures, await sign-out, and release any adapter-owned
resources through the ordinary service/plugin lifecycle. Keep React-only SDK providers
inside the optional integration package using existing plugin providers.

Check an adapter in its own tests with `assertAuthContract` from `@bitakit/core/testing`. It
drives the provider's login through `signIn` and rejects with the first broken rule: an
unstable snapshot, a missing unsubscribe, a non-string `user.id`, a `signOut` that resolves
before the user is cleared, or invalid `paths`.

```ts
import { assertAuthContract } from '@bitakit/core/testing';

await assertAuthContract(runtime.services.auth, {
  signIn: () => runtime.services.auth.signInWithPassword({ identifier: 'ada', password: 'test' }),
});
```

Auth.js and Clerk adapters are not implemented yet. Their native session/login APIs
must be mapped inside their optional packages; organizations, registration and password
recovery are not standardized by this small contract and stay on the provider's own service,
which `services.auth` exposes with the provider's full type. `@bitakit/better-auth` and
`@bitakit/strapi` (Users & Permissions, with registration, password reset and provider login)
are working references.

`organizationId` identifies the current settings scope when supplied by the provider; it
is not proof of organization membership. Server access checks remain with the provider.
See [Integrations](/docs/integrations) for available adapters and
[manual composition](/docs/concepts/manual-composition) for providing a contract without discovery.

## Server identity: the `requestContext` provider

[Server operations](/docs/concepts/server) learn who is calling from one server service in the
app that `provides: requestContext`. Its `resolve(request)` reads the request with the app's own
authentication and answers a `RequestIdentity`:

| Field          | Meaning                                                                                        |
| -------------- | ---------------------------------------------------------------------------------------------- |
| `user`         | The verified user (`id`, optional `name`, `email`), or `null` when signed out                  |
| `organization` | `{ id }` only for an active, enabled membership of this user; never just an ID the client sent |
| `member`       | The membership record (`id`, `role`), passed on as `ctx.member`                                |
| `reason`       | Why there is no organization: `'NO_ACTIVE_ORGANIZATION'` or `'NOT_A_MEMBER'`                   |
| `can`          | `(permission) => boolean \| Promise<boolean>` for `access: { permission }`; only `true` grants |

With Better Auth and its organization plugin:

```ts title="src/server/services/request-context.ts"
import { defineService, requestContext, type RequestIdentity } from '@bitakit/core/server';
import { auth } from '@/lib/auth'; // the app's Better Auth server instance

export default defineService(
  () => ({
    async resolve(request: Request): Promise<RequestIdentity> {
      const { headers } = request;
      const session = await auth.api.getSession({ headers });
      if (!session) return { user: null };
      const { id, name, email } = session.user;
      const user = { id, name, email };
      const organizationId = session.session.activeOrganizationId;
      if (!organizationId) return { user, organization: null };
      // Only an active, enabled membership of this user in this organization counts.
      const member = await auth.api.getActiveMember({ headers }).catch(() => null);
      if (
        !member ||
        member.organizationId !== organizationId ||
        member.userId !== id ||
        member.disabled === true
      )
        return { user, organization: null, reason: 'NOT_A_MEMBER' };
      return {
        user,
        organization: { id: organizationId },
        member: { id: member.id, role: member.role },
        can: async (permission) => {
          const permissions = Object.fromEntries(
            Object.entries(permission).map(([resource, operations]) => [resource, [...operations]]),
          );
          const result = await auth.api.hasPermission({ headers, body: { permissions } });
          return result.success === true;
        },
      };
    },
  }),
  { provides: requestContext },
);
```

`member.disabled` exists when the Better Auth member schema declares it
(`additionalFields: { disabled: { type: 'boolean', required: false, input: false } }`). Any other
authentication works the same way: verify the cookie, bearer token or gateway header with the
library you use, and answer `{ user, organization?, member?, can? }`.

The kernel copies and freezes the answer: a user only with a non-empty string `id`, an
organization only with a user and a non-empty `id`. It asks the provider once per call and only
for non-public operations; a provider that throws answers 500 and grants nothing. While an
operation needs a signed-in caller and no service provides `requestContext`, the server refuses
to start and names the file to add. Tests use the provider of `mountServer` instead
([testing](/docs/reference/testing#test-a-server-half)).

On the client, `remote` sends the `organizationId` of the `auth` snapshot with every call while a
user is signed in. The server compares it with the session's organization and answers `CONFLICT`
when the session has moved on, so a stale page never writes to another organization. The
snapshot's `organizationId` is still not proof of membership; only the provider decides.
