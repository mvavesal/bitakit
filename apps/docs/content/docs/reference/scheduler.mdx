title: Scheduler
description: Tasks, in-process schedules, runtime data sources and execution observation.

`@bitakit/scheduler` is an optional UI-free plugin. Croner owns cron, one-shot dates, timezones
and per-schedule overlap protection. Tasks and schedules run on the server: the package ships a
server half, so the generated server file installs the scheduler with the files in
`server/contributions/tasks|schedules/`. The kernel boots on its first call; boot it at process
start so schedules fire from the start (Next.js `instrumentation.ts`: in `register()`, only when
`process.env.NEXT_RUNTIME === 'nodejs'`, `await (await import('./bitakit.gen.server')).server.ready`).
A scheduled run has no request: pass what a task needs as `input`, and start a server task from
the browser through a server Action. Until the next minor version the old place
`contributions/tasks|schedules/` keeps running where it ran before, with a warning;
`bitakit migrate` moves those files. The package requires Core's contribution
installer context and ships its own `AGENTS.md` consumer guide and runnable server examples.

## Declarations

| API                | Fields / behavior                                                                                                                                   |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `defineTask`       | `{ input?, requires?, execute }`; parsed input, AbortSignal, `schedule`/`slot` of a scheduled run and feature-owned services/config/events/settings |
| `defineSchedule`   | `{ task, cron, input?, timezone?, paused? }` or `{ task, at, ... }`; `at` includes a UTC offset                                                     |
| Task files         | `server/contributions/tasks/<name>.ts`; dotted and record forms are equivalent                                                                      |
| Schedule files     | `server/contributions/schedules/<name>.ts`; separate namespace with the same ID convention                                                          |
| Generated maps     | `TaskMap` and `ScheduleMap`; mixed-case string references retain input/result checking                                                              |
| Manual composition | Named `schedulerPlugin` in `createRuntime`; `registerTask` accepts the same definition and feature context                                          |

Tasks are executable application code. Sources contain JSON-compatible schedule data only.
Domain authorization stays in the task or business service and applies to every invocation.
Task, source and schedule registration IDs in this new package must be unique ignoring case.

## Service contract

Obtain the service with `getService(services, scheduler)` using the exported `scheduler`
contract. Its actual service ID is `scheduler-engine`; plugin ID is `scheduler`.

| Method                                       | Contract                                                                             |
| -------------------------------------------- | ------------------------------------------------------------------------------------ |
| `run(taskId, input?, { schedule?, slot? }?)` | Await parsed/authorized execution and its result; schedule metadata grants no access |
| `runDue({ now?, within? }?)`                 | Run each schedule whose latest slot lies in `(now - within, now]`; settled results   |
| `registerTask(id, definition, context?)`     | Register code without discovery; returned async cleanup aborts and drains this task  |
| `registerSource(source)`                     | Register a data source; returns `ready`, `reload`, `dispose`, `Symbol.asyncDispose`  |
| `reload(sourceId?)`                          | Reload one or all sources; rejects on failure                                        |
| `unregisterSource(sourceId)`                 | Revoke and dispose a source; lower-priority schedules return                         |
| `registerSchedule(schedule, { priority? }?)` | One schedule as an owned source; default priority 100                                |
| `pause(scheduleId)` / `resume(scheduleId)`   | Runtime pause override, retained across reloads                                      |
| `list()` / `state`                           | Sanitized current status / Core observable store; no inputs, results or raw errors   |

Automatic timers activate after Core startup is ready and pause during lifecycle replacement.
Manual execution through the plugin also requires runtime readiness. Direct `createScheduler`
hosts own `start()` and `stop()` themselves. Await stop; tasks must cooperate with AbortSignal.
Never await owned cleanup from a task that cleanup must drain.

## Running schedules from a cron

In-process timers fire only while a server process lives. Serverless hosts (Vercel, Cloudflare,
Netlify) keep none, so let the host's cron call a route that runs `runDue`:

```ts title="src/plugins/cron/server/actions/tick.ts"
import { getService } from '@bitakit/core';
import { defineAction } from '@bitakit/core/server';
import { scheduler } from '@bitakit/scheduler';
import { z } from 'zod';

export default defineAction({
  access: 'user', // called by the route below as the system principal; not exposed
  input: z.object({ within: z.number().int().positive().max(86_400_000) }),
  execute: async ({ input, services }) =>
    (await getService(services, scheduler).runDue({ within: input.within })).map(
      ({ schedule, slot, status }) => ({ schedule, slot: slot.toISOString(), status }),
    ),
});
```

```ts title="src/app/api/cron/tick/route.ts"
import { timingSafeEqual } from 'node:crypto';
import { server } from '@/bitakit.gen.server';

export async function GET(request: Request) {
  const secret = process.env.CRON_SECRET;
  const given = Buffer.from(request.headers.get('authorization') ?? '');
  const expected = Buffer.from(`Bearer ${secret}`);
  if (!secret || given.length !== expected.length || !timingSafeEqual(given, expected))
    return new Response('Not allowed.', { status: 401 });
  return Response.json(await server.system('cron.tick').cron.tick({ within: 60_000 }));
}
```

`runDue({ now?, within? })` runs every enabled, unpaused schedule, code and source schedules
alike, whose latest slot (at or before `now`, in its timezone) lies in `(now - within, now]`.
`within` is in milliseconds (default 60000): call it every minute with the default, or once a day
with `within: 86_400_000` where the host's cron allows only daily jobs. Each due schedule runs once,
in parallel, through the public `run`, so interceptors see it as usual. The result has one entry
per due schedule: `status: 'fulfilled'` with `value`, `'rejected'` with `reason`, or `'skipped'`
while its previous run is still in progress in this process. Only the latest slot runs, never
every missed one.

The task receives `schedule` and `slot` (the planned time as a `Date`, also for timer runs).
Deduplication across instances is the task's or the app's job: a retried cron call, a second
instance or a living process whose timer fired the same slot can start it again, so claim
`schedule` + `slot` first, for example with a unique database row, and skip a claimed slot.

| Host                  | Cron that calls the route                                                  |
| --------------------- | -------------------------------------------------------------------------- |
| Vercel                | `crons` in `vercel.json`; sends `Authorization: Bearer $CRON_SECRET`       |
| Cloudflare            | Cron Triggers: a `scheduled()` handler fetches the route with the secret   |
| Netlify               | Scheduled Functions that fetch the route with the secret                   |
| GitHub Actions        | `on: schedule` with `curl -H "Authorization: Bearer …"`                    |
| A server or container | crontab: `* * * * * curl -fsS -H "Authorization: Bearer …" https://…/tick` |

## Sources and precedence

| Source field          | Meaning                                                              |
| --------------------- | -------------------------------------------------------------------- |
| `id`                  | Unique source ID, ignoring case                                      |
| `priority`            | Higher wins; default 0; feature defaults use -100                    |
| `load()`              | Promise of a complete schedule array, including each schedule's `id` |
| `subscribe(onChange)` | Optional change notification; returns unsubscribe                    |

Equal priorities sort case-folded source IDs by code-point order; last wins. Removing an
override restores the lower-priority default. Invalid snapshots retain the last valid state;
loads serialize and disposed sources cannot reactivate. Unchanged effective definitions keep
their timer and one-shot completion state. Removed schedules stop future triggers; running
calls drain normally, or are aborted when their task/scheduler is disposed.

| Helper                                        | Environment / behavior                                                         |
| --------------------------------------------- | ------------------------------------------------------------------------------ |
| `dataSource`                                  | Callback source; existing authorized DB/CMS services implement the contract    |
| `urlSource`                                   | Node/browser fetch; JSON or YAML; registration, reload or subscribed change    |
| `fileSource` from `@bitakit/scheduler/server` | Node-only runtime reads and directory watch, including atomic file replacement |
| `parseSchedules` / `parseScheduleDocument`    | Shared Zod validation and JSON/YAML parsing                                    |

Adapters are normal services: register in `onStart`, own disposal with `onStop` before awaiting
`ready`. Source errors reject explicit calls and reach the local error reporter; the service
store retains a source failure flag. Provider loads must settle; no forceful I/O termination.
The generated server file installs the scheduler with discovered tasks and schedules; only a host without discovery composes `schedulerPlugin` by hand. Node file code never enters client discovery.

## Observation and limits

All automatic and manual calls enter the same public `run` method, observed by normal
[service interceptors](/docs/concepts/interceptors). `callId`, `startedAt` and `durationMs`
correlate phases; observers may write through their own authorized logging services. Hooks are
not awaited and do not guarantee durable logs. Service interceptors already observe across
plugins and do not accept an Action-style `scope` option.

Events `scheduler.started`, `scheduler.completed` and `scheduler.failed` contain `task`, optional
`schedule` and a runtime-local `runId`. Input validation failures emit `failed` without `started`.
The event `runId` and interceptor `callId` are separate local correlation domains.

No persistence, exactly-once, distributed queue, leader election, replay of every missed slot
or closed-tab execution is provided. A schedule never overlaps itself in one process (timers
and `runDue`); manual calls and separate schedules may overlap. Error handling never silently retries a task.
