---
title: Work with AI coding agents
description: Give a coding agent the same map you use, with written rules, one place per task, checked names and one command to verify.
---

BitaKit is built so that a person and a coding agent find the same answer to "where does this
go?". This guide shows what an agent gets from a BitaKit app and how to brief it.

## What the agent reads

Apps created with `npx @bitakit/create-app` contain an `AGENTS.md` (and a `CLAUDE.md` that
imports it, which Claude Code reads) and the `bitakit-app-development` agent skill.
`npx @bitakit/cli init` adds the same files to an existing Next.js or TanStack Start app. Both
need version 0.2.2 or later.

The `AGENTS.md` block fits on one screen:

- a table that maps each task to its file, from a page to extending a feature you do not own;
- the rules: start small, bind every control to its Action, React only under `ui/`, and do not
  rebuild what BitaKit provides;
- the commands to create files and check the result, and a pointer to the skill.

Keep the block as it is and add your own product rules above or below it.

The skill holds the fuller workflow. Before a change the agent reads the installed packages,
runs `info` and `doctor`, and checks which layout renders the place it wants to use. It then
follows a recipe for the task (pages, Actions, services and events, slots, interceptors,
settings, tests), checks the result in the browser and tells you what it built and how it
connects. The skill is written to two folders, ready to commit:

| Folder                                    | Read by                                                      |
| ----------------------------------------- | ------------------------------------------------------------ |
| `.agents/skills/bitakit-app-development/` | Codex, and also Cursor, GitHub Copilot, Gemini CLI, OpenCode |
| `.claude/skills/bitakit-app-development/` | Claude Code                                                  |

An existing skill folder is never overwritten, so a team can adapt its copy.

### Use the skill

Open the agent in the app folder; Codex looks for skills only from the current folder up. Then
name the skill before your request:

```text
$bitakit-app-development Show the number of todos in the app header from a new summary plugin. Do not change the todos plugin.
```

That is the Codex form; in Claude Code write `/bitakit-app-development` instead, and in Cursor
type `/` and pick the skill. Agents also load the skill on their own when a request matches it;
naming it is the reliable way. The request above works in an app created with `--sample`; the
[skill's README](https://github.com/mvavesal/bitakit/blob/main/packages/cli/skills/bitakit-app-development/README.md)
lists more requests that build on that sample, one building block at a time.

## What the agent can run

| Command                                | What it gives the agent                                                             |
| -------------------------------------- | ----------------------------------------------------------------------------------- |
| `npx bitakit add action notes/archive` | The file in the right place, with the ID `notes.archive`                            |
| `npx bitakit add plugin notes`         | A new feature folder with a page, and its sidebar link when Shell is installed      |
| `npx bitakit info --json`              | The IDs your plugins declare: Actions, services, page URLs, events, settings, slots |
| `npm run typecheck`                    | An error for any unknown Action ID, service, event, setting key or slot name        |
| `npx bitakit doctor`                   | Wiring problems, each with its fix; exit code 1 when something is wrong             |

`info --json` reads plugin files without starting services or Actions, so it is safe to run at any
time. Installed packages such as Shell show `declarations: null`; their slots are listed in their
READMEs and in the generated types.

## Write a task brief

A good brief names the feature folder, the result and the check. For example:

```text
Add an "Archive" button to the notes page.
- Work only in src/plugins/notes/.
- The operation is a new Action notes.archive; bind the button to it with <Action>.
- When done, run npm run typecheck and npx bitakit doctor and fix what they report.
```

For a change to a feature the agent does not own, say so, and point it to the owner's contracts:

```text
Show the latest todo changes below the todo list.
- Do not edit src/plugins/todos/.
- Create src/plugins/activity/: listen to todos.changed and fill the todos.footer slot that todos declares.
```

[Extend from a second plugin](/docs/concepts/extend) is the worked example of that pattern.

## Review the result

A new feature is a new folder; an extension adds files to the extending plugin's own folder.
`git status --short src/plugins` shows at a glance whether the agent stayed in its feature.
Type checks and doctor catch wrong names and wiring; tests and review still decide whether the
behavior is right. Plugins are trusted code in one app, not a sandbox.
